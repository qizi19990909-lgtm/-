## 1. 第一版范围、模块与排期

### 1.1 横屏对手机网页的影响（之前定的是竖屏，现在改为横屏）
- **无法强制横屏**：iOS Safari 不支持锁定屏幕方向；Android Chrome 只有进入全屏后才能锁定。对策：竖着拿手机时显示「请横屏」遮罩，在首次点击时请求全屏并锁定方向（Android 生效）。
- **可视高度小**：横屏时浏览器地址栏和工具栏会占掉高度，6 寸手机实际约 320–390 CSS 像素高。1280×720 的逻辑画面会被缩小到 0.45–0.55 倍：110 px 高的角色在屏幕上只有约 50–60 CSS 像素，按钮至少要做到 80–90 逻辑像素。对策：引导用户「添加到主屏幕」（PWA 独立窗口，可去掉地址栏）。点选角色以底部头像栏为主，地图上的点击判定半径放大，并优先选中我方单位。
- **刘海和安全区在左右两侧**：底部 UI 和技能按钮要避开左右边缘约 44 像素。
- 包体和加载跟方向无关，见 5.3。**第一版只做横屏，不做竖屏（创意部已确认）**；但 UI 一律用锚点（Anchor）和容器（Container）布局，不写死坐标，以后加竖屏时不用推倒重做（这本来就是 Godot UI 的常规写法，不额外计工作量）。是否彻底去掉竖屏由老板决定。

### 1.2 首个可试玩版本（最小范围，比青石村切片更小）
目的：只验证玩法文档 8 节的验证目标①——**手机网页上的即时小队战好不好操作、好不好看**。
- 1 张单屏地图（挑战模式 3 波 + 1 个精英；外加无尽模式，供排行榜使用）。
- 2 个角色同时上阵：剑修男（近战）+ 弓手女（远程）——**建议一男一女**，尽早验证两套身体底板共用骨骼和动作是否穿帮；外观做白、蓝两档（蓝为换色），用来验证整套换图。
- 3 种武器：剑、弓、锤。这样能覆盖「得心应手」和「学艺不精」，例如弓手拿锤会把锤子射出去。
- 动作：8 个基础动作 + 1 个通用施法 + 2 职业 × 3 个攻击动作 = 15 个。
- 怪物 2 种 + 1 只精英，用 AI 生成的序列帧，不需要换装。
- 系统：点选角色、点地移动、自动战斗；每人 2 个技能，每个技能可单独设自动或手动；冰、火两种属性叠层；掉落（带稀有度）、背包、穿戴、强化（含 1 档贴纸）；死亡和复活；本地存档和存档码；本地排行榜（无尽模式最高波数）。
- **不做**：炼丹、布阵、拍卖行、极境、天赋树、角色收集、剧情、挂机和离线收益。
- 估计：程序 15–20 人天；美术 14–23 人天（v1.2：一男一女多出第二套底板和动作复查，约 +2–3 人天；前提见 1.5）。

### 1.3 青石村 1–10 级切片（第一版完整范围）
在首个可试玩版本的基础上增加：3 张地图 + 1 Boss（山贼头目；总经理的第一版建议，待老板确认；正式版 1–10 级按老板原话 5 张）；主角 + 2 名可收集角色（3 个头，各自性别固定），最多 3 人上阵；6 种武器（以玩法 3.8 为准）；冰火电暗 4 种属性；天赋树三条线（只开放 1–10 级节点）；炼丹和布阵各 5–8 个配方（放进玩家洞府系统）；装备 10 个槽位（武器/防具/饰品只作大类标签），稀有度 7 档中只掉白、绿、蓝、（紫）（绿装倍率 1.07、1 条词条）；强化与镶嵌（**建议切片内单件强化上限 +10**：10 槽总和最高 100，平均每件 +7 左右能达到第 1 档贴纸（>60），既能摸到特效又给后续区域留空间；配置按单件 30、总和 300、4 档贴纸预留）；练体极境 1 个（由剧情引导）；NPC 商店与模拟拍卖行；在线挂机与离线收益；练武场；新手剧情与引导；本地排行榜。

### 1.6 是否缩小范围
建议缩小：**先交付 1.2 节的可试玩版本，再决定是否做完整切片。**理由：①切片中炼丹、布阵、拍卖、极境的程序量约占一半，但这些系统是否好玩，取决于即时战斗手感是否成立；②美术的拆件产能还没有被验证；③越早让老板在手机上试玩，返工成本越低。

## 2. 骨骼动画：Spine 还是 Godot 自带 Skeleton2D
| 维度 | Spine（Esoteric Software） | Godot 自带 Skeleton2D + AnimationPlayer |
|---|---|---|
| 授权费 | 编辑器按人买断：Essential 标价 99 美元（当前促销 69 美元），Professional 标价 449 美元（当前促销 379 美元），含后续更新；年收入或融资超过 50 万美元必须买 Enterprise（2499 美元起，按年）。来源：https://esotericsoftware.com/spine-purchase | 免费（MIT 协议） |

| 功能 | Essential 有皮肤（skins）、IK，**没有网格、权重、变形、裁剪**（来源：purchase 页功能表）。本项目是 2 头身切片风格，不需要网格，Essential 够用 | 骨骼、关键帧、方法轨道（可做命中事件）；没有网格变形工具（不需要）；2D IK 属实验性功能 |

| **本机实测导出** | 4.7.2 + spine-godot 4.3 GDExtension，单线程且开启 Extensions Support 后**导出成功**（需要使用 dlink 导出模板，本机已有）。产物：主 wasm 1.5MB + side.wasm 44MB + spine 2.6MB，gzip 后合计约 11.6MB。**尚未在真机浏览器里运行验证** | 原有空项目导出：wasm 38MB，gzip 约 10.1MB |
| 包体差异 | 比纯引擎多约 1.5MB（gzip），另外动态链接模板体积略大 | 0 |
| CPU（实测，见 5.2） | 官方示例 spineboy 每单位约 65–75 µs | 15 骨骼测试角色每单位约 30 µs |
| 换装 | 皮肤/附件切换成熟，所有外观要打进图集，按职业分包加载 | 直接替换每个部件 Sprite2D 的贴图，最简单，可以按需加载单套贴图 |
| 工作流 | 动画师在 Spine 编辑器（图形界面）里制作，导出 .skel 和 .atlas。**AI 无法操作编辑器**，必须有人会用 Spine | 在 Godot 编辑器里制作，或者**用脚本和配置生成关键帧**（AI 可以写），质量较一般，但可迭代 |
| 版本锁定 | 每次升级 Godot 都要等对应版本的 spine-godot 构建 | 无 |
| 生态 | 淘宝、市场上的现成素材多为 Spine 格式（老板参考图来源） | 现成素材少 |

**推荐**：M0 和首个可试玩版本用 **Godot Skeleton2D**。动画数据（动作名、命中事件、挂点）按引擎无关的方式写进配置，以后切换 Spine 只需重做动画资源，逻辑层不用改。满足以下任一条件时，改用 **Spine Essential**（每个使用者一份授权，69–99 美元）：①找到会用 Spine 的动画师；②决定采购 Spine 素材做二次改造；③用 Godot 做出来的动作质量老板不满意。暂时不需要 Professional。

## 3. 换装方案
**规则**（美术规范 12 节、12.4）：10 个槽位中稀有度最低的一件 → 外观档 0–6（白绿蓝紫橙红暗金 7 档，与稀有度一一对应）→ 整套换图；集齐套装 → 显示暗金外观；武器按自身稀有度独立显示；全身强化总和 → 特效贴纸档（>60 / >180 / >222 /（建议加 >270））；只在换装时计算，战斗中不计算。

**实现（Skeleton2D 版）**
1. 所有角色共用一套骨骼场景 `hero_rig.tscn`，骨骼和插槽命名沿用美术规范 2.1。每个插槽是骨骼下的一个 Sprite2D，用 z_index 控制绘制顺序；动作需要时，用动画轨道临时改 z_index（相当于 Spine 的 draw order 关键帧）。
2. **外观 = 一份贴图表**：`outfits.csv` 按（job, gender, tier）给出每个插槽的贴图路径，换装时一次性设置各 Sprite2D 的 texture。男女两套身体底板共用同一骨骼、同一部件切分和锚点规范，动作通用；同职业同性别的角色共用身体和服装；头、发型、表情、配色属于角色，单独一张 `characters.csv`（head_tex、hair_front/back、gender、palette_id），头部切分和锚点全角色统一。
3. **换色档**（白、绿、蓝共用一个造型；同职业不同角色的服装配色也属换色）：第一版用**预先烘焙好的换色贴图**，不用运行时调色板着色器。原因是自定义材质会打断 2D 合批、增加 draw call（见 5.1）。
4. **武器**：`weapon_main` 骨骼下挂一个 Sprite2D，贴图按（weapon_type, tier）选取；所有武器统一握点（美术规范 12.3）；「错误握法」靠配置里的 grip_offset 和 grip_rotation 实现。投射类职业发射时生成投射物节点，使用该武器的投射图，飞行中旋转。
5. **强化贴纸**：在 fx_feet、fx_chest、back 三个骨骼挂点下挂特效节点（AnimatedSprite2D 序列帧或 GPUParticles2D），按贴纸档开关。配置预留 4 档，切片只做第 1 档（总和 >60）。特效 1 = 脚底光，特效 2 = 环绕粒子，特效 3 = 背后光效。设置中提供「只显示自己 / 降低特效」开关。
6. **部位放大**：缩放 6 根 scale_* 骨骼，受击判定用固定胶囊体，不受放大影响（美术规范 2.2）。
7. Spine 版对应关系：外观 = skin（按职业 + 性别 + 档位命名，头部另成一个 skin），运行时用 mix-and-match 组合皮肤（官方示例 03）；武器用 SpineSlotNode 或附件替换；贴纸挂在 SpineBoneNode 上。

**每个职业、每个性别要准备的资源**（服装男女同一设计，按各自版型分别出图）
- 外观部件（7 档：白/绿/蓝共用 1 套图换色，紫/橙/红/暗金各单独出图 → 5 套出图 + 2 套换色）：body（衣服）、body_detail（腰带/坠饰）、hand_L、hand_R、foot_L、foot_R、back（背饰/法宝）、cape（只有红和暗金档有）、headgear（职业标志物，比如斗笠和帽子可能随档位变化）→ **每档约 8–9 张部件图**。
- 角色头部（每个角色一套，切分和锚点统一）：head、hair_back、hair_front、表情（eye/brow/mouth × 6 种表情，可共用）；外加一份服装配色。
- 职业攻击动作 3 个（普攻、暴击、背击；阵法师只有 1 套：插旗/挑刺）；8 个基础动作 + 1 个通用施法由所有职业共用。
- 投射类职业（弓手、法师、阵法师）：所有 6 种武器都要有一张可旋转的投射图（各档换色）。
- 职业特效颜色：命中特效、施法光的色板。

**风险**
- **部件锚点不一致会穿帮**：全部 84 套外观、男女两套底板必须用同一模板拆件（同尺寸、同锚点、同关节位置）。需要先做「拆件模板 PSD + 自动检查脚本」（检查尺寸和锚点像素）。
- **AI 生成的部件风格漂移**：v8 是整张图，同一档在不同职业之间，AI 很难出一致的部件。必须人工统一线宽（美术规范规定描边 3px，2 倍源图为 6px）和色板。
- 大造型的外观（披风、大斗笠）在某些动作中会穿模，需要逐个动作检查。
- 图集和内存：每套外观约 9 张部件，按 2 倍源图约 256–512px，单套约 1–2MB 显存。只加载当前上阵角色的外观，不整包加载。
- 「9 件橙 1 件白显示白外观」玩家可能误以为是 bug，需要在 UI 里提示是哪件拉低了外观。

## 5. 手机同屏性能与排行榜

### 5.1 估算（估计）
- **同屏上限建议**：我方 5 人（骨骼动画）+ 怪物 ≤20 只（**含精英和 Boss**，序列帧为主，Boss 可以用骨骼；创意部已按此设计波次）+ 投射物 ≤40 + 阵法 ≤4 层。
- **骨骼数**：我方每人约 25 根（美术规范 2.1 清单，含 6 根缩放骨骼和 4 个特效挂点），5 人约 125 根；人形精英或 Boss 用 12–20 根；普通怪用帧动画，不用骨骼。
- **Draw call**：Godot 4 的 Compatibility 渲染器会把相邻、同贴图、同材质的 2D 元素合批。Y 排序让不同单位交错排列，会打断合批。估计每个骨骼角色 1–3 次、每只怪 1 次、特效和投射物 10–30 次、UI 10–20 次，**合计约 60–130 次**。对策：每个角色的部件打进同一张图集；不用逐单位自定义材质（所以换色用预烘焙贴图）；同类特效共用材质。

### 5.2 最小基准测试（本机实测，headless，只测 CPU 处理时间，不含 GPU 渲染）
项目在 `项目/修仙-技术验证/bench/`。环境：云电脑 x86（8 核）、Godot 4.7.2 原生 headless。统计 600 帧平均的 process 时间：
| 单位数 | Skeleton2D（15 骨骼 + 15 部件 + AnimationPlayer） | AnimatedSprite2D（6 帧） | Spine（官方示例 spineboy，骨骼比本项目多） |
|---|---|---|---|
| 10 | 0.29 ms | 0.04 ms | 0.96 ms |
| 60 | 2.1 ms | 0.29 ms | 3.9 ms |
| 120 | 3.3 ms | 0.11 ms | 7.7 ms |
| 240 | 6.6 ms | 0.15 ms | 18.3 ms |
解读：Skeleton2D 每单位约 30 µs，Spine 示例约 65–75 µs，帧动画几乎可以忽略。手机网页是单线程 wasm，CPU 也弱，**估计比本机慢 5–10 倍**：25 个骨骼单位约 4–8 ms（Skeleton2D），对 60 帧每帧 16.7 ms 的预算尚可；同样数量的 Spine 约 9–18 ms，偏紧。**这只是粗测**：没有测 GPU、填充率、特效和发热，结论需要在 M0 用真机确认。

### 5.3 低端手机网页的风险与对策
| 风险 | 对策 |
|---|---|
| 首次加载慢：引擎 gzip 后约 10MB（用 Spine 约 11.6MB），加上资源 | 托管端开 gzip 或 brotli；按地图和角色分包加载；开启 PWA 缓存；后期可编译精简模板（去掉 3D 等模块，估计 gzip 后可降到 5–7MB，需验证） |
| WebGL2 兼容性、iOS 内存上限 | 只用 Compatibility 渲染器；纹理控制在 2048px 以内；只加载上阵角色的外观；场景切换时释放资源 |
| 特效糊屏、发热掉帧 | 「降低特效 / 只显示自己特效」开关；粒子数量上限；按设备自动降档（帧率低于 40 持续 5 秒就关闭贴纸粒子） |
| 单线程卡顿导致音频爆音 | 音效从简；不在战斗中加载资源 |
| 浏览器存档丢失（清除数据、无痕模式、iOS 约 7 天不访问会清理、换域名） | 自动存档 + 备份档；申请 `navigator.storage.persist()`；存档码导出；试玩网址确定后不再更换 |

**真机验证方法（M0，约 1 人天）**：把压测项目导出为 Web，挂到静态托管，加一个 N 值滑杆（10/25/40）和 FPS 显示，用老板的手机加一台千元档安卓机，分别测横屏下 1 分钟的平均和最低帧率，以及首次加载时间。达标线（建议）：25 个单位时平均帧率 ≥50，首次加载在 4G 下 ≤15 秒。

### 5.4 排行榜
- **第一版：只做本地离线**（无尽最高波数、练武场每秒伤害、Boss 最快通关；每项本地 Top 10），约 1 人天。可选加入虚构 NPC 成绩作为追赶目标。单机数据可以被修改，本地榜不做防作弊，只加校验和以防存档损坏。
- **后期在线榜（只做简要估计）**：客户端数值不可信。可选方案：①简单校验（数值合理性上限、上传频率限制），便宜但容易被绕过；②**回放验证**：客户端上传随机种子、配置版本和操作日志，服务器用 headless Godot 重跑战斗，比对结果。这要求战斗逻辑确定性（固定步长、种子随机数、不依赖物理引擎），需要从第一版起在架构上预留（建议现在就预留）。成本估计：开发 8–15 人天；服务器方面，简单校验用 Serverless（如 Cloudflare Workers）可免费或约 35 元/月，回放重跑需要一台小型云服务器，约 50–150 元/月。如使用国内服务器和域名需要 ICP 备案；面向公众发布还涉及版号和实名、防沉迷等合规问题，届时另行评估。

### 6.2 AI 生成、占位与瓶颈
| 类别 | 方式 | 说明 |
|---|---|---|
| 概念设计、造型、配色 | **AI 生成** | 已在做（v8/v6），效果好 |
| 怪物（普通、精英） | **AI 逐帧 + 人工清理** | 不换装，可以用战士 GIF 那套流程，每只约 0.5–1 人天 |

| **玩家角色部件拆分与对齐** | **人工，属于瓶颈** | 每套独立外观估计 0.5–1 人天，换色约 0.1 人天 |

### 6.3 第一版只做哪些组合（建议）

## 8. 主要风险（技术侧）
1. 美术拆件与动作产能未经验证，这是最大的工期风险。M0 先拿 1 个角色做完整流程，测出单套外观的实际耗时。
2. 手机网页性能和加载未经真机验证（5.3）。
3. 即时小队战在 6 寸横屏上的操作手感，靠首个可试玩版本尽早验证。
4. 内容量大：完整 60 级是数年工作量，只能按区域切片推进。
5. 在线榜要求战斗逻辑确定，必须从第一版起按确定性架构写，否则以后要重写。
6. Spine 路线有编辑器授权、需要会用的人、版本锁定三重依赖；Godot 路线的动作质量可能不如专业 Spine 动画。
